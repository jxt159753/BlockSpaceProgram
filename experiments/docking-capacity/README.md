# 对接合并容量原型

样船覆盖 36、72、144、288 个零件，27、54、108 个船体节点，以及每个船体节点 1,024、4,096、8,192 格。原型使用真实的 `flight_layout` 实体同步、飞行状态和 Sable 刚体。 [设计决策 #140](https://github.com/jxt159753/BlockSpaceProgram/issues/140)

## 测量方法

- 每个烘焙零件由 4 × 4 × 4 格平滑石和切制铜组成，按 1/4 比例摆放。零件在同一平面连接，每半艘船各有一个指令舱、一个对接口和两个分级。船体节点是 1 格厚的实心平滑石板，分别为 32 × 32、64 × 64、64 × 128 格。船体挂在相邻零件的上下两面。两半船通过一个对接连接组成完整的零件图。
- 稳态场景直接生成该零件图。一次性试验从相距 4 m 的两艘刚体开始，将间距调到 0.125 m，由常规对接检测完成捕获。来船的最后一个零件预置损坏，合并后检查下标超过 63 的损坏位。解除对接时核对两船 UUID、分级和损坏。轨道重建由旁观者进入局部物理区触发。重启从同一世界内保存的 Sable 实体和子区恢复。
- 稳态复用 `/bsp_bench` 的采样器。每档先测空场景，再在相同机位测一艘刚体。两次均预热 8 s、采样 12 s。漂浮状态在轨道局部物理区绕竖直轴以 0.2 rad/s 开始自转。预算取 #22 的 MSPT 中位数 50 ms 和帧耗时 P95 16.7 ms。 [基准设置](../../docs/benchmark.md#复测步骤)
- `layout_wire` 是 `FLIGHT_STREAM_CODEC` 实际写入实体物品组件的未压缩字节数，含布局分支标记。`layout_nbt` 是存档中该组件作为独立 NBT 标签的字节数。`entity_nbt` 是完整飞船实体快照的未压缩 NBT 字节数。
- `TRACK` 是服务端开始追踪实体的时间。`RECEIVED` 是客户端收到整个布局的时间。`SHOWN` 取同机客户端渲染烘焙零件且全部船体渲染区段均已编译的首帧。`watch` 让观察者在主世界从追踪范围外移动到固定机位，同时记录 `ENTER`。两端用本机时钟关联时间戳。
- 原型用 `BigInteger` 临时拓宽节点掩码，以字节数组存储损坏和分级块的成员。上限设为 288 个零件、108 个船体节点和 576 级，以便覆盖试验档位。传入 `-PdockingCapacityWideNbt` 时将布局 NBT 的解码记账上限从 2 MiB 提到 16 MiB。线上的 NBT 内容与数据长度一致。游戏传输层仍使用本来的包限制。

单船压测使用一种重复零件和一种船体材质。推进、着陆腿、采集船体的装配耗时及多人追踪开销尚未测试。原型只在 `-PdockingCapacity` 下编译，正式代码和现有配置由正常构建加载。

## 复测

按照 [基准设置](../../docs/benchmark.md#复测步骤) 准备种子 `68` 的超平坦存档。Minecraft 1.21.1、NeoForge 21.1.267 和 Java 21。两端各使用 3 GiB 最大堆，把 Sable 2.0.6 放入 `runs/dockingCapacity/<名称>/server/mods/` 和 `client/mods/`。使用本机开发端口。关闭垂直同步，确认客户端的 `options.txt` 中 `maxFps:260` 对应「无限」，并核对报告的 `fps_limit` 为 `null`。

```powershell
.\gradlew.bat --offline build
.\gradlew.bat --offline -PdockingCapacity build
.\gradlew.bat -PdockingCapacity -PdockingCapacityWideNbt runDockingCapacityServer
```

服务端显示 `Done` 后，在另一终端启动客户端。

```powershell
.\gradlew.bat -PdockingCapacity -PdockingCapacityWideNbt '-PdockingCapacityJoin=127.0.0.1:25565' runDockingCapacityClient
```

1. 由权限等级 2 的在线玩家执行 `/bsp_capacity steady landed 72 27 1024 8 12`。分别将参数换成 `landed`、`drifting` 和各档的零件数、船体节点数、每节点方块数。用 `trial.id` 对齐两端 `blockspaceprogram/benchmarks/` 的 JSON。
2. 在设有 Sable 的试验服依次执行 `/bsp_capacity ops spawn 72`、`ops dock`、`ops undock`、`ops orbit`、`ops persist`。每次等服务端记录对应的 `CAPACITY TICK` 或 `CAPACITY PERSIST`。档位 144、288 重复同样的操作。保存并关闭服务器。重启后到主世界的 X=0、288、864 各查看一次飞船，记录 `op=restart`。
3. 使用单独的试验存档，两端去掉 `-PdockingCapacityWideNbt`，执行 `/bsp_capacity watch 72 27 8192`。核对客户端连接结果。再在开启实验 NBT 参数的试验服执行同一命令，核对 `TRACK`、`SHOWN` 和 `client/screenshots/` 的截图。
4. 在可渲染最大载荷的试验服执行 `/bsp_capacity ops save_max`。关闭并复制整个世界到另一套运行目录，两边都移除 Sable。连接同版本的专用服，执行 `/bsp_capacity ops read_max`，在日志核对 `blocks=221184 sable=false`。

## 实测

Windows 11，Intel Core Ultra 9 275HX，NVIDIA GeForce RTX 5070 Laptop GPU，Java 21.0.11。Minecraft 1.21.1、NeoForge 21.1.267、Sable 2.0.6 专用服与客户端同机运行。两端堆上限 3 GiB，未安装 Create。客户端为 1280 × 720、Fancy、视野 70°、视距 6、模拟距离 5。两端报告通过版本和 `trial.id` 核对。客户端关闭了云、实体阴影、垂直同步和帧率上限。 [性能测量基线 `73526b8`](https://github.com/jxt159753/BlockSpaceProgram/commit/73526b8bac7e52dcb510903e6d2e71c26eb27583)

使用现有 2 MiB 记账上限时，客户端追踪最大载荷后因 `NbtAccounterException` 断开。失败的数据包是 `clientbound/minecraft:set_entity_data`。这档船体有 221,184 格。稳态表的最大节点数来自另一档，为 315 个节点。

开启 16 MiB 实验记账上限后，最大样船完整收包。第一轮截图可见船体，烘焙零件受实体位置的距离剔除。实体原点在指令舱下方 128 格。补测把布局原点移到指令舱，保持船体几何和组件字节数。用 `9655bb7` 上的原型复测，从开始追踪到完整解出 99 个节点为 1,126 ms，到完整显示为 1,520 ms。从移动观察者到完整显示共 2,407 ms。 [首帧截图](evidence/max-layout.png)

把同一最大载荷样船写入轨道层存档并正常关闭专用服。复制存档到无 Sable 的 Minecraft 1.21.1、NeoForge 21.1.267 专用服。无 Sable 的客户端成功连接，服务端从存档读回 72 个零件、27 个船体节点和 221,184 格船体。

普通构建和开启原型的构建均通过，共 124 项 JUnit 测试。普通构建的 JAR 中无原型类。

### 单次操作

每个值是实际发生操作的整个服务器刻，单位为 ms。三档各含 27 个船体节点，每节点 1,024 格。72 件为会话中的首个对接样本。

| 合并零件数 | 对接合并 | 解除对接 | 进入物理区重建 | 重启后加载 |
| ---: | ---: | ---: | ---: | ---: |
| 72 | 656.80 | 412.98 | 383.13 | 272.44 |
| 144 | 301.66 | 331.49 | 309.47 | 167.73 |
| 288 | 294.58 | 320.72 | 359.04 | 100.60 |

三档合并后的最高损坏下标分别为 85、157、301，均包含两个原船分级块。解对接恢复了两艘船的 UUID、各自两级和来船损坏。实际进入局部物理区触发了轨道快照重建。完整重启后，三艘船均恢复同样的布局、原船分级块和高位损坏状态。

## 决定

维护者确认采用方案 A。默认上限定为 72 个零件、54 个船体节点、144 级。对应零件和船体节点档的帧耗时 P95 最高为 6.42 ms，布局组件约 1.01 MB。144 级可容纳两艘各用满 72 级的装配船。原型的一次性场景使用两个分级块，共四级。

代码绝对上限定为 288 个零件、108 个船体节点、576 级。288 个零件和 108 个船体节点分别测到，组合上限还需要正式实现的专用服验收。576 级按每零件两级的现有规则推导。合并还要满足整船布局的同步预算。正式实现要实测最大允许构型的客户端接收和显示，并报告导致对接拒绝的上限项。 [Issue #140 的决定](https://github.com/jxt159753/BlockSpaceProgram/issues/140#决定)
